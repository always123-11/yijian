# AIGC 辅助开发记录

本文件记录本项目开发过程中**真实发生**的 AIGC 辅助过程，用于作业「4. AIGC 使用要求」。
所有案例都包含：我提出的需求 → AI 提供的内容 → 实际效果 → 我做的人工修改与验证。

> 说明：本项目使用的 AIGC 工具是 **DeepSeek Harness 中的编码助手**（具备读写文件、
> 执行命令、运行测试的能力）。除下列记录外，代码框架与界面由我提出设计与需求后
> 由助手生成，**每一段关键逻辑我都通过单元测试或实际运行做了验证**。

## 案例 1：关卡文本的缩进处理导致棋盘整体错位

| 项目 | 内容 |
| --- | --- |
| **子任务** | 用三引号字符串书写关卡，并解析成棋盘 |
| **AIGC 技术** | 代码生成（DeepSeek 编码助手） |
| **提示词** | 「关卡用多行字符串表示，`.` 是空格子，`^v<>` 是箭头。写一个 `grid_from_text` 把字符串解析成每行一个字符串的列表。」 |
| **AI 生成内容** | 返回 `[line for line in text.strip("\n").splitlines() if line.strip() != ""]`，即只去掉首尾换行、过滤空行。 |
| **实际效果** | **关卡全部错位。** 因为关卡是写在函数里缩进的三引号字符串，每行前面都带着 8 个空格的公共缩进，`strip("\n")` 并不会去掉它们；结果第 0 行变成 `        .^.^..`，箭头被整体平移。 |
| **人工修改** | 改用 `textwrap.dedent(text)` 去掉公共缩进，再把空格统一替换成 `.`；并补充注释说明「可以直接把关卡写成代码里缩进的三引号字符串」。 |
| **验证方式** | 新增单元测试 `test_leading_indent_is_stripped` 与 `test_space_means_empty`；并用 `tools/check_levels.py` 重新校验 8 个关卡。 |

**收获**：AI 给出的"看起来对"的一行代码，忽略了 Python 三引号字符串的实际缩进语义。
这个问题不会报错，只会让所有关卡悄悄变形——必须靠测试才能发现。

## 案例 2：关卡设计中致命的"互相阻挡"死局

| 项目 | 内容 |
| --- | --- |
| **子任务** | 设计 8 个「保证可以通过」的关卡 |
| **AIGC 技术** | 代码生成 + 算法分析 |
| **提示词** | 「帮我设计 8 个箭头消除关卡，难度递增，并且**每一关都必须可以通关**。怎么保证？」 |
| **AI 生成内容** | 提供了一批 `6×6`～`10×9` 的关卡字符画；同时给出一个精确求解器 `core/solver.py`（记忆化 DFS 搜索消除顺序，返回最少步数）。 |
| **实际效果** | **第一版 8 个关卡里有 6 个不可解。** 例如第 2 关里 `>` 与 `<` 在同一行面对面，`^` 与 `v` 在同一列面对面：这类箭头会互相挡住，**永远无法消除**。求解器直接返回"无解"，`ensure_move_limits()` 打印出 `FAIL`。 |
| **原因分析** | 从规则本身可以证明：若把箭头 A 从棋盘上移除，只可能让别的箭头路径**变短**，绝不会让某个箭头路径变长。因此 A 一旦挡住 B，在 A 消失前 B 永远出不去；若 A、B 互相挡住，二者都永远出不去。**同一直线上相向而行的两个箭头是硬死锁。** |
| **人工修改** | 逐关重排方向，保证同一行/同一列**不存在相向的箭头对**；把求解器接入关卡校验，任何一关不可解就让整体失败。最终 8 关全部通过校验（最少步数分别为 6/7/4/4/9/8/8/12）。 |
| **验证方式** | `tests/test_playthrough.py::test_every_level_completable` 用求解器给出的顺序**真实走一遍**每一关，确认能清空棋盘。 |

**收获**：AI 能很快生成"看起来合理"的布局，但它并不理解规则背后的**可解性约束**。
是求解器（可验证的算法）+ 我给出的死锁分析，才把"保证可通关"这件事真正落实。
这也是本项目里最有价值的一次人机配合。

## 案例 3：点击处理破坏了失败状态，导致失败界面永远不出现

| 项目 | 内容 |
| --- | --- |
| **子任务** | 点击棋盘后切换界面场景（通关 / 失败） |
| **AIGC 技术** | 代码生成（DeepSeek 编码助手） |
| **提示词** | 「写 `click_cell`：调用 `board.click()`，根据返回值播放动画，并在 `status` 为 `solved` 时进入通关界面、`failed`/`stuck` 时进入失败界面。」 |
| **AI 生成内容** | 生成的方法末尾多了一行 `self.board.status = "playing" if result.status == "playing" else ""`，意图是"避免重复触发"。 |
| **实际效果** | **失败界面永远不出现。** 这一行把 `board.status` 直接改成了空串，于是界面读取 `board.status == "stuck"` 永远为假；更严重的是 `Board.click()` 内部用 `status != "playing"` 判断是否继续接受输入，状态被清空后规则层与界面层的状态语义被搅在一起。 |
| **人工修改** | 把"是否还接受输入"从 `status` 中**拆出来**，新增独立的 `Board.accepts_input` 标志：`status` 只描述局面（`playing/solved/failed/stuck`），`accepts_input` 才决定是否还能点击；并删掉 UI 里那行改写状态代码。 |
| **验证方式** | 新增 `test_failed_scene_renders`（把机会上限压到 2，反复点被挡箭头，断言 `scene == FAILED` 且 `board.status == "failed"`）；并用 `tools/screenshot.py` 生成真实的失败界面截图确认。 |

**收获**：AI 为了"修复"一个想象中的重复触发问题，顺手覆盖了状态字段，属于典型的
**过度防御式修改**。教训是把"局面状态"和"输入许可"两个概念分开建模，
状态只由规则层写入、界面层只读。

## 案例 4（附带）：pygame 重启后字体缓存失效

| 项目 | 内容 |
| --- | --- |
| **子任务** | 编写界面测试，保证测试之间互不干扰 |
| **AIGC 技术** | 错误诊断 + 代码修改 |
| **提示词** | 「运行 `python -m unittest discover -s tests` 时，前几个测试通过，后面报 `pygame.error: Surface is not initialized` 和 `Invalid font (font module quit since font created)`，帮我定位并修复。」 |
| **AI 生成内容** | 定位到根因：有一个测试会调用 `ui.game.main()`，而它在结束时执行 `pygame.quit()`，会关闭 video system 并使**已创建的所有 Font 对象失效**；而测试里的显示表面和字体都是"只初始化一次"的。 |
| **实际效果** | 修复前 25 个测试中有 2 个报错。按建议改造后：① 每个测试方法开头检查并按需重建 `display.set_mode()`；② 在 `ui/render.py` 增加 `reset_fonts()` 清空字体缓存。 |
| **人工修改** | 保留了 `reset_fonts()` 并加上中文注释解释原因，避免以后有人再次踩坑。 |
| **验证方式** | `python -m unittest discover -s tests` → **25 个测试全部通过**。 |

**收获**：这类"全局状态被中途销毁"的问题靠读代码很难发现，需要**真正跑一遍测试**才能暴露。
